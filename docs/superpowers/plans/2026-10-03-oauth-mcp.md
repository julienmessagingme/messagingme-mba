# OAuth 2.1 devant le serveur MCP : plan (lot 2 du plan « Engage Me pour Claude Code »)

**Spec** : `docs/superpowers/specs/2026-10-03-oauth-mcp-design.md` (1942a137). Elle fait foi ; ce plan dit l'ordre,
les fichiers, les interfaces et les tests attendus.

## Méthode de livraison

**Implémenteur par lot, puis UNE relecture indépendante du diff, en deux livraisons** : 2a (l'API, tâches 1 à 8) et
2b (la console, tâches 9 et 10). Cette méthode parce que la production emprunte ce chemin (des clients appellent
`/mcp`), que le lot ouvre une surface d'authentification publique, et que ses invariants (adresse annoncée égale à
l'adresse appelée, rotation des jetons, rôle relu à chaque appel) demandent un œil en plus des tests. Pas de workflow
de relecture. L'essai réel qui clôt la feature : depuis Claude Code sur le PC de Julien, `https://api.messagingme.app/mcp`
ajouté sans clé, connexion Google, « Autoriser », lecture des derniers messages d'un fil, puis révocation depuis la
console et nouvelle connexion exigée ; une adresse Google jamais vue qui crée son espace ; le même serveur ajouté en
connecteur dans claude.ai.

## Contraintes globales

- Toute entrée non fiable passe par Zod en `safeParse` : paramètres de `/oauth/authorize`, corps de `/oauth/token`,
  `/oauth/revoke` et des routes de consentement, jetons signés relus. Jamais de `as` sur une entrée externe.
- Filtrage `tenant_id = $1` sur chaque requête d'un espace (le pooler contourne la RLS).
- Aucun jeton, code, empreinte ni `code_verifier` dans un journal, une erreur ou une trace d'audit.
- `/oauth/token` et `/oauth/revoke` : erreurs en 4xx au format OAuth, jamais en 5xx (Cloudflare remplace leur corps),
  `Cache-Control: no-store`.
- La politique de sécurité de l'API (`src/http/entetes-securite.ts`) ne change pas.
- Adresses dérivées de `PUBLIC_API_URL` (`src/lib/adresses-publiques.ts`), jamais de l'en-tête `Host` ; module non
  monté si elle est vide.
- Durées en constantes nommées : code 60 s, accès 3 600 s, renouvellement 30 jours sans usage et 90 jours au plus.
- Pas de tiret cadratin ni demi-cadratin, dans le code comme dans les textes.
- 🔴 **Fichiers de câblage partagés** (`src/server.ts`, `src/index.ts`, `src/worker.ts`) : annonce aux sessions
  voisines avant de les toucher, et commit en plomberie sur origin.

## Livraison 2a : l'API

### Tâche 1. Migration (numéro lu dans `db/migrations/` d'origin au moment de l'écrire, 0204 au 2026-10-03)

- `oauth_autorisations` : `id uuid` (clé primaire, défaut aléatoire), `tenant_id` (cascade depuis `tenants`),
  `user_id` (cascade depuis `users` : `deleteUser` exige un `on delete` sur toute clé vers `users`), `client_id text`
  (CHECK : l'un des deux identifiants de la spec), `scopes text[]` (CHECK : non vide et inclus dans `mcp:read`,
  `mcp:write`), `resource text`, `acces_hash text` et `acces_expire_le`, `refresh_hash text`,
  `refresh_precedent_hash text`, `refresh_expire_le`, `refresh_max_le`, `cree_le`, `dernier_usage_le`,
  `revoque_le`. Index uniques partiels sur `acces_hash` et `refresh_hash` (non nuls), index sur
  `refresh_precedent_hash`, index `(tenant_id, cree_le desc)` pour la liste.
- `oauth_codes` : `hash` (clé primaire), `autorisation_id` (cascade), `code_challenge`, `redirect_uri`, `expire_le`,
  `utilise_le`.
- Additive : appliquée AVANT le `up` (le code neuf l'écrit), après lecture de `pg_stat_activity`, relue en base juste
  après (colonnes, CHECK sous leur nom, `confdeltype = 'c'`, index et prédicats, tables vides). Ligne du compteur de
  `CLAUDE.md` écrite dans le commit qui prend le numéro.

### Tâche 2. Le noyau pur : `src/oauth/`

- `clients.ts` : `CLIENTS_OAUTH` (les deux fiches de la spec, recopiées), `clientConnu(id): ClientOauth | null`,
  `adresseDeRetourAcceptee(client, uri): boolean`. Claude Code : schéma `http`, hôte exactement `localhost` ou
  `127.0.0.1`, tout port, chemin exactement `/callback`, ni identifiants, ni fragment. claude.ai : égalité exacte.
- `pkce.ts` : `verifierPkce(verifier, challenge): boolean` en S256 (base64url du SHA-256), `verifier` de 43 à 128
  caractères `[A-Za-z0-9-._~]`, comparaison à temps constant.
- `jetons.ts` : `nouveauJeton(prefixe: 'mbo_' | 'mbr_' | 'mbc_'): { brut, empreinte }` (32 octets aléatoires,
  base64url, empreinte SHA-256), `formeDeJeton(brut, prefixe): boolean`, les constantes de durée.
- `metadonnees.ts` : `metadonneesRessource(base)`, `metadonneesServeur(base)`, `enTeteWwwAuthenticate(base, erreur?)`.
- `src/auth/token.ts` gagne `signDemandeOauth`/`verifyDemandeOauth` (`kind: 'oauth_demande'`, 10 min : client,
  adresse de retour, défi PKCE, droits, `state`, ressource) et `signChoixOauth`/`verifyChoixOauth`
  (`kind: 'oauth_choix'`, 5 min : identité, empreinte de la demande). `verifySession` les refuse déjà (`kind`).
- Tests (`tests/oauth-noyau.test.ts`) : vecteur de l'annexe B de la RFC 7636 ; adresses de retour piégées
  (`http://localhost@evil.test/callback`, `http://localhost.evil.test:1/callback`, `https://localhost/callback`,
  `/callback/x`, `?x=1`, `#f`, `http://[::1]:5/callback`) refusées, `localhost` et `127.0.0.1` sur trois ports
  acceptés ; égalité exacte pour claude.ai ; métadonnées construites sur la base donnée (champs REQUIRED de la
  RFC 8414 présents, `code_challenge_methods_supported` = `["S256"]`, aucun `registration_endpoint`) ; une demande
  signée ne passe pas `verifySession`, ni `verifyChoice`, et inversement.

### Tâche 3. Le store : `src/oauth/store.pg.ts` (`PgOauthStore`)

- `creerAutorisation(entree: { tenantId, userId, clientId, scopes, resource, code: { empreinte, challenge, redirectUri } }): Promise<{ autorisationId }>` en une transaction.
- `consommerCode(empreinte): Promise<{ autorisationId, tenantId, clientId, challenge, redirectUri, scopes, resource } | null>` : `update ... set utilise_le = now() where hash = $1 and utilise_le is null and expire_le > now() returning`, donc un code ne sert qu'une fois, même en concurrence.
- `poserJetons(autorisationId, { acces, refresh, accesExpireLe, refreshExpireLe, refreshMaxLe })`.
- `renouveler(empreinteRefresh, nouveaux): Promise<'ok' | 'rejeu' | 'inconnu'>` : rotation (l'ancien passe en
  `refresh_precedent_hash`) ; une empreinte égale à `refresh_precedent_hash` révoque l'autorisation et rend `rejeu`.
  Il refuse aussi une autorisation dont la personne n'est plus admin ou désactivée.
- `resoudreAcces(empreinte): Promise<AccesOauth | null>`, une seule requête jointe (autorisation, `users`,
  `tenants`) : `{ autorisationId, tenantId, userId, scopes, tenantStatus, valide }`, `valide` faux si révoquée, échue,
  compte désactivé ou rôle autre qu'`admin`. Met à jour `dernier_usage_le` au plus une fois par minute.
- `revoquerParJeton(empreinte)`, `lister(tenantId)`, `revoquer(tenantId, id): Promise<boolean>`, `purger(): Promise<number>`
  (codes échus depuis une heure, autorisations révoquées ou expirées depuis 30 jours, par paquets bornés).
- Tests d'intégration (CI seulement, jamais en local : la base locale est la production) : code à usage unique,
  deux consommations simultanées dont une seule gagne ; rotation ; rejeu qui révoque ; rôle rétrogradé qui invalide
  accès et renouvellement ; cascade à la suppression du compte ; `lister` et `revoquer` refusent l'autorisation d'un
  autre espace ; purge.

### Tâche 4. La garde : un jeton `mbo_` sur `/mcp`

- `makeRequireApiKey` (`src/auth/api-key.ts`) reçoit un quatrième paramètre REQUIS, `oauth: { resoudreAcces(empreinte) }`
  (`PgOauthStore`), et aiguille sur le préfixe : `mba_` comme aujourd'hui, `mbo_` vers l'OAuth, avec le même ordre
  (format avant empreinte, budget des empreintes inconnues, plafond de l'ESPACE, partagé avec `/v1`).
- Accès OAuth : `req.auth = { userId: 'oauth:<autorisation>', tenantId, role: 'api' }` (jamais le vrai rôle),
  `req.apiScopes` = droits de l'autorisation, et deux champs neufs : `req.apiAcces = { type: 'cle' | 'oauth', id }`,
  `req.apiPersonne = { userId } | null`. Invalide ou inconnu : 401 ; espace suspendu : 403 `tenant_locked`.
- Le journal d'usage range l'accès sous `oauth:<autorisation>` (sans `|`).
- `/v1` et le relais refusent un jeton OAuth par leurs droits (`requireScope`, `DROIT_RELAIS`) ; un test le prouve.
- Tests : `tests/oauth-garde.test.ts` (aiguillage, refus, plafond de l'espace commun aux clés et aux jetons, rôle
  `api`), et `scripts/auto-attaque.mts` : un jeton `mbo_` inventé sur `/v1` et `/mcp`, 401.

### Tâche 5. `/mcp` : le 401 qui ouvre la connexion, et la personne

- `src/http/mcp.ts` : sur un 401, `WWW-Authenticate` de `enTeteWwwAuthenticate` (avec `error="invalid_token"` quand
  un jeton `mbo_` a été présenté), seulement si l'hôte appelé est celui de `PUBLIC_API_URL`. Ni `/v1`, ni 403, ni 429.
- `ContexteMcp` (`src/mcp/serveur.ts`) gagne `personne: { userId: string } | null`, rempli depuis `req.apiPersonne`.
- `reply_in_open_window` passe la personne comme auteur (origine `mcp` inchangée) ; `assign_conversation` la passe
  comme acteur. Avec une clé, `null` comme aujourd'hui. Le commentaire des widgets (« ses droits sont donnés par un
  administrateur ») reste vrai : seul un admin autorise.
- Tests : en-tête présent sur `api.` et absent sur `mba.`, absent sur `/v1` ; réponse signée de la personne avec un
  jeton, `null` avec une clé.

### Tâche 6. Les routes OAuth : `src/http/oauth.ts` (classe `anonyme`) et `src/http/oauth-consentement.ts` (classe `tenant`)

- Registre (`src/server.ts`) : `entree('oauth', 'anonyme', deps.oauth, ...)`, monté seulement si `PUBLIC_API_URL` est
  posée ; `entree('oauthConsentement', 'tenant', deps.oauthConsentement, ...)` sous `g.admin`. Câblage dans
  `src/index.ts`.
- Routes de la spec, section 1, avec leurs règles : `authorize` sans redirection sur client ou adresse inconnus ;
  `token` (`authorization_code` : code consommé, PKCE vérifié, `redirect_uri` et `client_id` égaux à ceux du code,
  `resource` égale si fournie ; `refresh_token` : rotation, `invalid_grant` sur rejeu) ; `revoke` toujours 200.
  Lecteur de formulaires limité à la portée (modèle `src/http/contact-vitrine.ts`).
- Consentement : `consentement/demande` (rend client, hôte de retour, droits) ; `consentement/google` (vérifie le
  jeton Google ; adresse inconnue : crée l'espace par le MÊME chemin que `/auth/google`, extrait en une fonction
  partagée, jamais recopié ; rend la preuve `oauth_choix` et les espaces avec `admin: boolean`) ;
  `consentement/autoriser` (preuve + demande + espace) ; `POST /tenants/:tenantId/oauth/autoriser` (session console).
  Les deux autorisations passent par UNE fonction `autoriser(personne, espace, demande)` qui relit le rôle en base,
  refuse un non-admin, crée l'autorisation et le code, journalise `oauth.autorise`, et rend
  `<redirect_uri>?code&state&iss`.
- `GET /tenants/:tenantId/oauth/autorisations` et `DELETE .../:id` (journal `oauth.revoque`).
- Plafonds : `PlafondPartage` sur les échecs de `/oauth/token` et sur `consentement/google` (création d'espaces).
- `scripts/auto-attaque.mts` : chaque route anonyme dans `OUVERTES` avec sa raison, `FAUSSES_AUTORITES.oauth`, et des
  sondes : code inventé, mauvais `code_verifier`, renouvellement inventé, client inconnu à `authorize` (aucune
  redirection), tous refusés. `tests/scope-tenant.test.ts` couvre les routes `tenant` sans changement.
- Tests (`tests/http-oauth.test.ts`) : le parcours complet avec des faux (demande, consentement, code, échange,
  appel `/mcp`, renouvellement, rejeu, révocation) ; non-admin refusé ; demande expirée ; métadonnées servies aux deux
  adresses ; 404 de tout le module sans `PUBLIC_API_URL`.

### Tâche 7. La purge et le script des fiches

- `src/worker.ts` : `taches.programmer('retention-oauth', 6 h, ...)` sur `PgOauthStore.purger`, avec `echecDeBalayage`.
- `scripts/oauth-fiches.mts` (`npm run oauth:fiches`) : relit les deux fiches publiées et dit si elles divergent de
  `CLIENTS_OAUTH` ; hors de `npm test` (réseau), une ligne dans `DEPLOY.md`.

### Tâche 8. La documentation de 2a

- `documentation.md` : l'OAuth dans le domaine MCP et § 7 (routes, jetons, garde, rôle relu, adresses).
- `CLAUDE.md` : la ligne du compteur de migrations, et le piège « OAuth seulement sur `api.` ».
- `wip.md` : l'état du lot et l'étape de l'essai réel.

**Ordre de déploiement 2a** : CI verte lue job par job ; `compose build mba-api` ; `migrate` (après `pg_stat_activity`)
et relecture en base ; `up -d --build` de `mba-api` ET des workers (la purge) ; rechargement NPM après `mba-api` sain ;
contrôle public (`/health` des deux portes, `curl -sI .../.well-known/oauth-authorization-server` montre les en-têtes de
l'API, `/oauth/token` répond en 400 à un client en ligne de commande) ; `npm run oauth:fiches`. Si Cloudflare bloque une
route machine, Julien pose la règle « Skip » de la spec, section 7.

## Rayon de souffle à vérifier par la relecture

- `makeRequireApiKey` a d'autres appelants que `/mcp` : `/v1` et le relais doivent garder exactement leur
  comportement pour une clé (mêmes codes, même plafond, même budget).
- La sonde 13 de l'auto-attaque (session de console et clé inventée sur les routes `cle-api`) doit rester verte.
- `deleteUser` : la nouvelle clé étrangère vers `users` doit être en cascade, sinon la suppression d'un compte échoue.
- `/auth/google` : l'extraction de son chemin de création d'espace ne doit rien changer à sa réponse.
